底层方案：P2P 连接层

一、定位

一句话：给定任意一个 info_hash，找到全网对该 info_hash 感兴趣的节点，与其中任意节点建立加密的点对点 WireGuard 隧道，并向上层提供统一的隧道传输接口。

不关心：上层跑什么协议、传什么数据、是不是群聊、有没有 Git。

---

二、职责边界

做的事 不做的事
通过公共 BT DHT 发现节点 不建 DHT、不建 Tracker
通过 PEX 滚雪球收集节点 不建信令服务器
在 BT peer 上交换 WG 公钥 不存任何业务数据
UDP 打洞 / IPv6 直连 不建中继、不建 STUN/TURN
建立并维护 WireGuard 隧道 不关心上层协议
提供隧道就绪回调 不做消息签名、存储、撤回
维护稀疏邻居表 不做全网状连接

---

三、模块划分

```text
p2p-conn/
├── discovery/       # BT DHT/PEX 节点发现
├── signaling/       # BT peer 上的自定义握手交换
├── tunnel/          # WireGuard 打洞与隧道管理
├── neighbor/        # 邻居表维护与替换策略
└── api/             # 对上层暴露的统一接口
```

四、模块详细设计

4.1 discovery：节点发现

输入：info_hash（或 .torrent 文件）

输出：活跃 peer 列表 [IP:Port]

流程：

```text
1. 客户端启动 libtorrent 会话。
2. 加载 .torrent 或磁力链接，加入 swarm。
3. 启动 DHT 节点（使用 BT 客户端内置的公共 DHT 网络）。
4. 启动 PEX 扩展。
5. 通过 DHT 查找 info_hash 对应的 peers。
6. 对每个已连接 peer 发起 PEX 请求，获取其 peer 列表。
7. 滚雪球式迭代，持续收集新 peer。
8. 输出去重后的 IP:Port 列表。
```

关键点：

· 不做种、不下载文件内容，只利用 BT 的 peer 发现能力。
· 可以只连接 metadata 交换，不实际传输文件分片。
· 公共 DHT 是基础设施，不是本系统运营的服务器。

输出示例：

```json
[
  {"ip": "2001:db8::1", "port": 6881, "source": "dht"},
  {"ip": "203.0.113.5", "port": 51413, "source": "pex"},
  {"ip": "198.51.100.7", "port": 6889, "source": "pex"}
]
```

4.2 signaling：BT peer 上的自定义握手

输入：peer IP:Port

输出：对方 P2P 身份信息

握手协议：

```json
// 请求
{
  "type": "p2p_hello",
  "version": 1,
  "network_id": "info_hash 或上层自定义命名空间",
  "ed25519_pub": "base64...",
  "wg_pub": "base64...",
  "wg_port": 51820,
  "timestamp_ms": 1730000000123,
  "signature": "Ed25519(上述字段)"
}

// 响应
{
  "type": "p2p_hello_ack",
  "version": 1,
  "network_id": "...",
  "ed25519_pub": "base64...",
  "wg_pub": "base64...",
  "wg_port": 51820,
  "timestamp_ms": 1730000000456,
  "signature": "Ed25519(上述字段)"
}
```

验证：

1. network_id 是否匹配。
2. Ed25519 签名是否有效。
3. 时间戳是否在可接受窗口内（可选）。
4. 如果上层有成员列表，检查公钥是否在白名单中。

输出：

```json
{
  "ed25519_pub": "...",
  "wg_pub": "...",
  "wg_port": 51820,
  "observed_ip": "203.0.113.5",
  "observed_port": 51413
}
```

关键点：

· 握手走 BT peer 连接，不需要额外服务器。
· BT 扩展协议（BEP 10）支持任意自定义消息。
· 即使 BT 连接随后断开，WG 隧道可以独立存活。

---

4.3 tunnel：WireGuard 打洞与隧道管理

输入：对方身份信息（IP、WG 公钥、WG 端口）

输出：可用的 WireGuard 隧道

打洞流程：

```text
1. 判断网络类型：
   a. 双方都有公网 IPv6 → 直接直连。
   b. 至少一方有公网 IPv4 → 公网方监听，另一方主动连。
   c. 双方都在 NAT 后 → UDP 打洞。

2. UDP 打洞：
   a. 双方同时向对方的公网 IP:WG端口 发送 UDP 探测包。
   b. 锥形 NAT：第一个包打开映射，第二个包到达，打洞成功。
   c. 对称 NAT：映射端口不可预测，打洞失败。

3. 打洞成功：
   a. 配置 WireGuard peer。
   b. 启动 keepalive。
   c. 隧道就绪。

4. 打洞失败：
   a. 标记该 peer 为不可直连。
   b. 如果上层有中继策略，交给上层处理。
   c. 底层不建中继。
```

WireGuard 配置：

```ini
[Interface]
PrivateKey = 本节点WG私钥
ListenPort = 51820
Address = 10.66.0.1/32

[Peer]
PublicKey = 对方WG公钥
AllowedIPs = 10.66.0.2/32
Endpoint = 对方公网IP:WG端口
PersistentKeepalive = 25
```

隧道状态机：

```text
IDLE → HANDSHAKING → CONNECTED → STALE → IDLE
         │                │
         │                └── keepalive 失败 → STALE
         └── 打洞失败 → IDLE
```

关键点：

· 每个节点只维护 5～8 条活跃隧道。
· 优先 IPv6 直连，其次 IPv4 直连，最后 UDP 打洞。
· 底层不做中继。打不通就打不通，由上层决定是否降级。

4.4 neighbor：邻居表维护

邻居表结构：

```json
{
  "peer_id": "ed25519_pub",
  "wg_pub": "...",
  "endpoint": "203.0.113.5:51820",
  "state": "CONNECTED",
  "rtt_ms": 23,
  "last_seen": 1730000000123,
  "ipv6": true,
  "priority": 100
}
```

维护策略：

策略 说明
最大邻居数 8
最小邻居数 3
掉线检测 keepalive 超时 25 秒
补充策略 从候选表按优先级选
优先级 IPv6 > IPv4 直连 > 打洞；RTT 低 > 高；在线久 > 短
淘汰策略 掉线、高延迟、频繁重连的降级
候选表 通过 discovery 和 signaling 持续补充

关键点：

· 邻居表是稀疏的，不是全网状。
· 每个节点只连少数邻居，通过上层 Gossip 实现全网传播。
· 底层只负责“连上”，不负责“传播”。

4.5 api：对上层暴露的接口

```text
P2PConnection
│
├── init(config) -> Connection
│   config: {
│     info_hash: "...",
│     ed25519_keypair: ...,
│     wg_keypair: ...,
│     max_neighbors: 8,
│     min_neighbors: 3
│   }
│
├── start() -> void
│   启动 discovery + signaling + tunnel + neighbor 全部模块
│
├── stop() -> void
│   关闭所有隧道，停止 discovery
│
├── on_peer_discovered(callback)
│   发现新 peer 时回调
│
├── on_tunnel_ready(callback)
│   隧道就绪时回调，参数为 Tunnel 对象
│
├── on_tunnel_closed(callback)
│   隧道关闭时回调
│
├── get_neighbors() -> [NeighborInfo]
│   获取当前活跃邻居列表
│
├── connect_to(peer_info) -> Tunnel
│   主动连接指定 peer
│
└── broadcast(payload) -> void
    向所有活跃邻居发送数据（可选，上层也可自己遍历邻居）
```

Tunnel 对象：

```text
Tunnel
├── send(data: bytes) -> void
├── on_data(callback)
├── close() -> void
├── remote_pub: string
├── local_ip: string
├── remote_ip: string
└── state: enum
```

上层使用示例：

```python
conn = P2PConnection.init({
    "info_hash": "abc123...",
    "ed25519_keypair": load_or_create(),
    "wg_keypair": load_or_create(),
    "max_neighbors": 8
})

conn.on_tunnel_ready(lambda tunnel: {
    tunnel.on_data(handle_message),
    tunnel.send(hello_payload)
})

conn.start()

# 上层完全不需要知道 BT、DHT、PEX、WG 的存在
```

---

六、关键设计决策

决策 理由
用公共 BT DHT 做发现 不建服务器，利用现成基础设施
用 BT 扩展协议做信令 复用已有 peer 连接，不需要额外通道
用 WireGuard 做隧道 内核态加密，性能高，配置简单
稀疏邻居（5～8） 避免 O(N²) 隧道爆炸
不建中继 保持纯去中心化，打不通由上层处理
底层不管业务 通用可复用，群聊只是第一个 Demo
Pull 式同步交给上层 底层只提供隧道，不关心传播模型

---

七、已知限制

限制 说明
对称 NAT UDP 打洞可能失败，底层不做中继
公共 DHT 可见性 你的 IP 对 BT swarm 中其他 peer 可见
冷启动 全网无人在线时无法发现节点
邻居数上限 稀疏连接导致传播延迟，由上层 Gossip 补偿
无身份准入 底层不验证业务身份，由上层签名和白名单处理

---

八、总结

底层只做四件事：

1. 发现：用公共 BT DHT/PEX 找到节点 IP。
2. 握手：在 BT peer 上交换 WG 公钥和签名。
3. 打洞：UDP 打洞或 IPv6 直连，建立 WG 隧道。
4. 维护：保持 5～8 条活跃隧道，掉线自动补充。

底层不做的：

· 不建服务器、不建 DHT、不建 Tracker、不建中继。
· 不关心上层跑什么、传什么、存什么。
· 不做消息签名、时间戳、Git、撤回。

上层想跑什么就跑什么，群聊只是第一个应用。
